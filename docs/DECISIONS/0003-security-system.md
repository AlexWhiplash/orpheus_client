# ADR 0003: Система безопасности входа (PIN, Duress, Panic Wipe)

## Статус
Принято. **Расширено 2026-07-26** (1.1.8+45): duress-гейт вынесен за пределы `DatabaseService` — серверные данные, стек Navigator, экран «Безопасность», экспорт аккаунта, сеттеры конфига; см. раздел 3 и «Отрицательные».

## Контекст
Приложение Orpheus — защищённый мессенджер с E2E шифрованием. Однако приложение открывалось без какой-либо защиты входа, что создавало риск при физическом доступе к устройству.

Требования:
1. Опциональная защита PIN-кодом (по умолчанию — вход открыт)
2. "Код принуждения" (duress code) — второй PIN, показывающий пустой профиль
3. Экстренное удаление данных при тройном нажатии кнопки питания
4. Сохранение полной анонимности (без привязки к email/телефону)

## Решение

### 1. Модель безопасности (`SecurityConfig`)
- 6-значный PIN-код с хешированием SHA-256 + соль (10000 итераций)
- Отдельный duress-код с собственной солью
- Отдельный **код удаления (wipe code)** с собственной солью
- Прогрессивная блокировка: 5 попыток → 30 сек, 10 → 1 мин, 15 → 5 мин, 20 → 30 мин
- Опциональный auto-wipe после N неудачных попыток

### 2. Сервис авторизации (`AuthService`)
- Singleton с хранением конфигурации в `FlutterSecureStorage`
- Проверка PIN возвращает enum: `success | duress | invalid | lockedOut | autoWipe`
- Флаг `isDuressMode` для переключения режима отображения данных
- Проверка PIN также поддерживает `wipeCode` (код удаления), который **требует подтверждения удержанием** в UI

### 3. Duress Mode (режим принуждения)
- При вводе duress-кода приложение разблокируется, но `isDuressMode = true`
- `DatabaseService` проверяет флаг и возвращает пустые данные:
  - `getContacts()` → `[]`
  - `getMessagesForContact()` → `[]`
  - `getProfileStats()` → `{contacts: 0, messages: 0, sent: 0}`
- **Обновление 2026-07-26 (1.1.8+45): гейта БД оказалось недостаточно.** Добавлено:
  - **серверные данные**: `RoomsService._pubkey` и `SupportChatService._pubkey` → `null` (комнаты и чат с разработчиком живут на сервере, гейт БД их не касался); у поддержки отдельная ветка в `loadMessages` — пустой результат и `_error == null`, иначе текст ошибки сам стал бы tell'ом;
  - **стек Navigator**: лок — оверлей в `MaterialApp.builder`, поэтому маршруты, открытые до лока, оставались смонтированными с расшифрованными данными (реальный чат, диалог экспорта с root seed). `PushedRouteTracker` (NavigatorObserver) + `dropRoutesAboveHome()` на `NavigatorState.removeRoute` — синхронно, без анимации, пока непрозрачный лок ещё нарисован; три точки вызова: duress-вход, завершение wipe, настоящий PIN после duress-сессии. `popUntil` не подходит: маршрут доигрывает выход ~300 мс уже без лока;
  - **экран «Безопасность»** не сообщает, что код принуждения/удаления настроены; секции остаются видимыми в состоянии «не настроено» (исчезновение секции — тоже tell), а путь настройки ведёт в `PinSetupScreen`, где шаг 0 требует `PinVerifyResult.success`;
  - **экспорт аккаунта** в duress требует PIN приложения, а не код устройства (у наблюдателя код устройства обычно есть, а экспорт отдаёт 32-байтный root seed);
  - **сеттеры конфига безопасности** (auto-wipe, panic-жест, биометрия, автолок, retention) и тумблер «имя звонящего на локскрине» — no-op; гейт в КАЖДОМ сеттере, а не в `_saveConfig` (иначе сломается `disableDuressCode`). Осознанный компромисс: переключатель визуально отскакивает назад;
  - **гигиена лога**: строка входа в duress не называет режим (журнал достижим из этой же сессии).
- **Точность формулировки**: реальные СОХРАНЁННЫЕ данные остаются на диске и лишь скрыты, но входящие личные сообщения, пришедшие ВО ВРЕМЯ duress-сессии, теряются навсегда — строгий mutual-add спрашивает `isContact`, а он в duress отдаёт `false`, и кадр дропается до записи в БД.

### 4. Panic Wipe
- `PanicWipeService` отслеживает переходы в `AppLifecycleState.paused`
- Важное ограничение: без нативного кода Flutter не перехватывает физические нажатия кнопки питания.
  Текущая реализация — приближение: **3 быстрых ухода приложения в background** (обычно серия блокировок/разблокировок
  экрана или быстрое сворачивание приложения).
- По умолчанию жест **выключен**, чтобы избежать случайного удаления данных
- Выполняется полный wipe: ключи, БД, конфигурация безопасности

### 5. Блокировка при сворачивании
- При переходе в background приложение блокируется (если PIN включен)
- При возврате требуется ввод PIN или биометрия

## Последствия

### Положительные
- Защита от физического доступа к устройству
- Plausible deniability через duress-код
- Экстренное удаление при угрозе
- Анонимность сохранена (нет привязки к внешним идентификаторам)

### Отрицательные
- Пользователь может забыть PIN (восстановление только через приватный ключ)
- Тройное нажатие может случайно сработать (маловероятно)
- Duress mode не скрывает факт наличия приложения
- **Код удаления (wipe code), введённый с локскрина, не доходит до `performWipe`**: `showDialog` вызывается из виджета внутри `MaterialApp.builder`, у которого нет Navigator в предках → `FlutterError`. Авто-wipe и panic-жест работают. Лечить слоем подтверждения внутри самого `LockScreen`; вариант «через `navigatorKey`» неверен — диалог уедет под непрозрачный оверлей лока.
- **Известные оставшиеся tell'ы duress** (открыты на 1.1.8+45): уведомления комнат и ответов поддержки всплывают (тела обезличены, но факт виден); экран отладочных логов достижим 5 секретными тапами, включая «поделиться» файлом; `clearChatHistory` — единственный путь удаления без duress-гейта; входящие личные сообщения во время duress теряются; push-изолят к duress слеп (свой экземпляр `AuthService`).

### Риски
- При потере приватного ключа и забытом PIN — данные утеряны навсегда
- Атакующий может заставить ввести оба кода
- Любой новый экран/сервис, который читает данные НЕ через `DatabaseService`, по умолчанию оказывается вне гейта duress (урок комнат и чата поддержки) — гейт нужно ставить осознанно при каждой новой поверхности данных.

## Альтернативы рассмотренные

1. **Пароль вместо PIN** — отвергнуто, т.к. менее удобно на мобильных устройствах
2. **Только биометрия** — отвергнуто, т.к. не везде доступна и может быть обойдена
3. **Удаление данных в duress** — отвергнуто, т.к. пустой профиль менее подозрителен
4. **Shake-to-wipe** — может быть добавлено позже как дополнительный механизм
