# Orpheus Client — обзор безопасности (проблемы и рекомендации)

## Цель документа
Зафиксировать **реальные риски** и “границы обещаний” безопасности клиента, чтобы:
- понимать, от каких угроз защищаемся, а от каких — нет;
- приоритизировать исправления;
- не строить процессы/маркетинг на предположениях.

## Что уже сделано (клиент)
- **E2E для сообщений**: шифрование на клиенте (X25519 + ChaCha20‑Poly1305).
- **Secure storage для ключей**: ключи и security config хранятся в `flutter_secure_storage`.
- **Privacy в уведомлениях**: текст сообщения не показывается в уведомлении (`notification_service.dart:645`). Ограничение: гейтится только СОДЕРЖИМОЕ — в duress‑сессии уведомления комнат и поддержки по‑прежнему всплывают (`lib/main.dart:541`, `lib/services/incoming_message_handler.dart:113-116`).
- **Защита UI при физическом доступе**: PIN + lockout ladder + duress mode + авто‑wipe по неудачным попыткам + panic‑жест (см. ADR). **Код удаления (wipe code) с локскрина НЕ РАБОТАЕТ** — см. P0 ниже.

## Критичные проблемы безопасности (P0/P1)

### P0 — Код удаления (wipe code) с локскрина не срабатывает
**Где**: `lib/screens/lock_screen.dart:242` (`_showWipeConfirmDialog`), контекст лока — `lib/main.dart:1247-1256` (`MaterialApp.builder`).

**Наблюдение**: `LockScreen` рисуется оверлеем внутри `builder`, который оборачивает Navigator СВЕРХУ, поэтому `showDialog(context: context)` не находит Navigator в предках и бросает `FlutterError`. Ветка `PinVerifyResult.wipeCode` (`lock_screen.dart:213-215`) до `widget.onWipe(WipeReason.wipeCode)` не доходит НИКОГДА. Авто‑wipe (`:226-227`) работает.

**Риск**: пользователь под принуждением вводит код удаления и получает ничего — ни стирания, ни обратной связи; функция обещана в UI и в документации.

**Рекомендация**: слой подтверждения ВНУТРИ самого `LockScreen`. Наивный фикс «через `navigatorKey`» неверен: диалог уедет в root Navigator, то есть ПОД непрозрачный оверлей лока, и станет невидимым и некликабельным.

### P0 — TURN credentials и endpoint захардкожены в клиенте
**Где**: `lib/services/webrtc_service.dart` (`rtcConfiguration`).

**Почему это опасно**:
- утечка инфраструктуры и статических кредов (их нельзя “считать секретом”);
- риск абьюза TURN (затраты/DoS);
- невозможность нормальной ротации/разделения сред.

**Рекомендация**:
- вынести TURN параметры на сервер (выдача краткоживущих credentials, например TURN REST API);
- убрать креды из репозитория; обеспечить ротацию.

### P0 — Wipe может быть неполным (физическое удаление данных)
> **✅ Устранено (SEC-1 + SEC-5/LOGIC-7/ARCH-7):** локальная БД теперь **зашифрована** (SQLCipher, ключ из Android Keystore, схема v7); `performWipe()` удаляет файл БД (включая ключ шифрования), очищает **всё** secure storage целиком (`deleteAll`) и работает best-effort (сбой шага не отменяет остальные). Ниже — исходное наблюдение аудита (историческое).

**Где**: `lib/services/auth_service.dart` (`performWipe()`), `lib/services/database_service.dart`.

**Наблюдение по коду (на момент аудита)**:
- wipe закрывал БД через `DatabaseService.instance.close()`, но **не удалял файл БД** явно.
- `DatabaseService` хранил сообщения в расшифрованном виде в SQLite.

**Риск**:
- после “wipe” на устройстве могут остаться recoverable данные (контакты/сообщения) в файле БД/кэше.

**Рекомендация**:
- сделать wipe “жёстким”: удаление файла БД через `deleteDatabase(...)`/удаление директории данных (аккуратно);
- добавить тест/проверку, что после wipe и повторной инициализации данные отсутствуют.

### P0 — Слабая/неочевидная аутентификация некоторых HTTP API (системный риск)
**Где**:
- `lib/services/support_chat_service.dart` использует заголовок `X-Pubkey`.
- `lib/license_screen.dart` отправляет `pubkey` в body для `/api/activate-promo`.
- `lib/services/websocket_service.dart` отправляет HTTP fallback для `/api/signal` с `sender_pubkey` в body.

**Почему это опасно**:
Если сервер доверяет “pubkey из заголовка/body” без доказательства владения ключом/сессией, возможны:
- подмена отправителя сигналов/активаций;
- спам/абьюз.

**Рекомендация** (для всей системы, не только клиента):
- сервер должен авторизовать запросы через связанный контекст (например: токен, подпись, привязка к WS‑сессии);
- для критичных сигналов использовать подпись (Ed25519) или иной проверяемый механизм, если модель угроз требует.

## Важные риски (P2)

### P2 — PIN hashing не memory‑hard
> **✅ Устранено (SEC-8):** PIN, duress‑код и wipe‑код теперь хэшируются **настоящим Argon2id** (memory‑hard, ~19 МБ, OWASP‑минимум) вместо 10k SHA‑256. PIN, заданные до обновления, проверяются по старой схеме и авто‑апгрейдятся на Argon2id при первом успешном входе. Ниже — исходное наблюдение (историческое).

**Где (на момент аудита)**: `lib/services/auth_service.dart` (`_hashPin`, 10k SHA‑256 iterations).

**Риск**:
Если атакующий получает доступ к security config (salt+hash), перебор 6‑значного PIN может быть относительно дешёвым на GPU/ASIC.

### P2 — Логи могут содержать чувствительные данные
> **✅ Устранено (SEC-2 + QUAL-1/OPS-6):** телеметрия теперь **opt‑in, выключена по умолчанию** и санитизирована (удалены `peer_pubkey`/`*_pubkey`/`*_key`/`device_info`), тумблер — в экране отладочных логов. `DebugLogger` в release‑сборке **не пишет в системный logcat** (`kDebugMode`), а чувствительные события безопасности убраны из логов. Ниже — исходное наблюдение (историческое).

**Где (на момент аудита)**: `DebugLogger` + полная телеметрия (HTTP/WS payload, фоновые события).

**Риск**:
Полная телеметрия могла раскрыть токены/метаданные и технические контексты.

## Duress mode: что он гарантирует и что нет

**Гейты, которые есть (1.1.8+45, покрыты тестами)**:
- чтения БД отдают пустое (контакты/сообщения/статистика/заметки), деструктивные методы — no‑op;
- **серверные** данные тоже закрыты: `RoomsService._pubkey` и `SupportChatService._pubkey` → `null` (`lib/services/rooms_service.dart:25`, `lib/services/support_chat_service.dart:47`); у поддержки отдельная ветка в `loadMessages` — ПУСТО и `_error == null`, чтобы текст ошибки сам не стал tell'ом (`:62`); живой ответ по WS — no‑op (`:219`);
- **UI реальной сессии не переезжает в duress**: лок — оверлей поверх Navigator (`lib/main.dart:1247-1256`), поэтому маршруты, открытые до лока, оставались смонтированными с уже расшифрованными данными (реальный чат, диалог экспорта аккаунта с root seed). `PushedRouteTracker` + `dropRoutesAboveHome()` (`lib/main.dart:75`, `:129`) снимают их синхронно и без анимации в трёх точках: duress‑вход (`:978`), завершение wipe (`:821`), настоящий PIN после duress‑сессии (`:940`);
- экран «Безопасность» НЕ признаётся, что код принуждения/код удаления настроены; секции остаются видимыми в состоянии «не настроено» (`lib/screens/security_settings_screen.dart:201-203`);
- экспорт аккаунта в duress требует PIN ПРИЛОЖЕНИЯ, а не код устройства (`lib/screens/settings_screen.dart:139`);
- пять сеттеров конфига — no‑op (auto‑wipe, panic‑жест, биометрия, автолок, retention: `lib/services/auth_service.dart:477,486,497,513,588`), плюс тумблер «имя звонящего на локскрине» (`security_settings_screen.dart:304`);
- журнал отладки не называет режим (`lib/main.dart:970`).

**Не гарантирует (открытые дефекты, НЕ считать закрытыми)**:
- **код удаления с локскрина не работает вообще**: `showDialog` в `lib/screens/lock_screen.dart:242` вызывается из виджета внутри `MaterialApp.builder` (`lib/main.dart:1247-1256`), у которого нет Navigator в предках → `FlutterError`, `onWipe(WipeReason.wipeCode)` недостижим. Авто‑wipe (`lock_screen.dart:226-227`) и panic‑жест работают;
- **уведомления не гейтятся duress**: сообщения комнат (`lib/main.dart:541`) и ответы поддержки (`lib/services/incoming_message_handler.dart:113-116`) поднимают локальные уведомления. Тела обезличены (`notification_service.dart:645`), но само появление уведомления доказывает наблюдателю наличие скрытого реального аккаунта;
- **экран отладочных логов достижим из duress‑сессии** (5 секретных тапов, `lib/screens/settings_screen.dart:119-126`): RAM‑буфер плюс кнопка «поделиться», отдающая файл лога;
- `clearChatHistory` — единственный путь удаления БЕЗ duress‑гейта (`lib/services/database_service.dart:1066`): удаляет РЕАЛЬНЫЕ сообщения безвозвратно;
- **входящие личные сообщения во время duress теряются НАВСЕГДА**: строгий mutual‑add спрашивает `isContact`, а он в duress возвращает `false` (`lib/services/database_service.dart:489`) → кадр дропается до записи (`lib/services/incoming_message_handler.dart:128`), сервер уже считает его доставленным;
- физическое отсутствие данных на диске и защита при компрометации устройства — как и раньше, не обещаются.

## Рекомендуемый порядок исправлений (roadmap по безопасности)
- **P0**: починить код удаления с локскрина (слой подтверждения внутри `LockScreen`).
- **P0**: убрать TURN креды из клиента, сделать выдачу краткоживущих credentials.
- **P0**: сделать wipe физически удаляющим локальные данные.
- **P1**: duress — закрыть вход на экран отладочных логов, загейтить уведомления (комнаты + поддержка), поставить гейт в `clearChatHistory`, перестать терять входящие (складывать в `PendingInboxStorage` вместо дропа).
- **P0/P1**: пересмотреть модель авторизации HTTP endpoints (support/promo/signal).
- **P2**: улучшить PIN hashing или явно ограничить обещания модели угроз.
- **P2**: redaction для логов.
